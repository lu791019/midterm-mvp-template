# 期末專題追蹤機制

> 從期中活動結束到期末，追蹤各組專題進度。

---

## 追蹤節奏

| 頻率 | 方式 | 內容 |
|------|------|------|
| 每週 | 各組在群組回報 | 用下方的週報模板，1 分鐘填完 |
| 每 2 週 | 講師文字回饋 | 針對週報給建議，標出風險 |
| 期末前 2 週 | 線上 check-in（15 min/組）| 確認能 Demo、解決卡關 |

---

## 週報模板（每週一份，貼在群組）

```
📋 第 __ 週進度（__月__日）
組別：_____

✅ 本週完成：
- 

🔜 下週目標：
- 

🚧 卡關/風險：
- （沒有就寫「無」）

📊 完成度自評：_____ %
```

> 講師只需看「卡關/風險」欄位，有問題的才需要介入。

---

## 里程碑對照表

從期中到期末，建議的進度節奏：

| 週次 | 里程碑 | 驗收標準 |
|------|--------|---------|
| 第 1 週 | 資料確認 | 資料已下載/已能存取，跑過 EDA 知道長什麼樣 |
| 第 2 週 | Pipeline MVP | CSV → SQLite 三表跑通（可以用期中活動的程式碼改） |
| 第 3 週 | 技術升級選一項 | Docker / Airflow / BigQuery / dbt 至少跑通一個 |
| 第 4 週 | 整合測試 | 完整 Pipeline 端對端跑通，有產出 |
| 第 5 週 | 打包 + 文件 | README 完整、能 Demo、有部署（至少 Docker） |
| 期末 | Demo | 團隊上台展示完整系統 |

> 不是每組都一樣快，這是參考節奏。重點是第 2 週結束前要有東西能跑。

---

## 風險燈號

講師在看週報時，快速標記：

| 燈號 | 判斷標準 | 行動 |
|------|---------|------|
| 🟢 正常 | 進度符合里程碑，無卡關 | 按讚，不用介入 |
| 🟡 注意 | 進度落後 1 週，或有卡關但還在嘗試 | 群組給建議，指個方向 |
| 🔴 需介入 | 進度落後 2 週以上，或卡死不動 | 約 15 分鐘線上 check-in |

---

## 期末前 2 週 Check-in 問題清單

每組 15 分鐘，問以下問題：

1. **Pipeline 跑得通嗎？** — 從 input 到 output 端對端 show 一次
2. **升級了什麼？** — 跟期中 MVP 比，多了什麼技術？
3. **分工均勻嗎？** — 每個人負責什麼，都有碰 code 嗎？
4. **Demo 準備了嗎？** — 投影片或畫面準備好了？
5. **最擔心什麼？** — 期末前最大的風險是什麼？

---

## 期中 → 期末的連結

在期中活動收尾時，跟學員說清楚這件事：

> 「今天做的個人 MVP，就是你們期末團專的原型。
>
> 下一步：
> 1. 把今天的 repo push 到你的 GitHub
> 2. 團隊決定用誰的 MVP 當基礎，或合併多個
> 3. 每週用週報模板回報進度
> 4. 後續課程學的 Docker / Airflow / GCP，直接套在這個專案上
>
> 期末 Demo 的評分標準比今天多兩項：**團隊協作** 和 **技術升級深度**。」

## 追蹤工具建議

| 方式 | 優點 | 缺點 |
|------|------|------|
| **LINE 群組** | 學員最常用，回報門檻低 | 訊息容易被洗掉 |
| **HackMD 共筆** | 每組一頁，歷史可追溯 | 要另外開連結 |
| **GitHub Issues** | 跟 code 在一起，工程師習慣 | 學員可能不熟 |
| **Notion** | 最美觀，看板式追蹤 | 要設定權限 |

> 建議：LINE 群組回報 + 講師自己用一份 spreadsheet 記錄燈號。最簡單。
